# Architecture Differential Audit — GBA_Emulator vs mGBA / SkyEmu / VBA-M

- **Date:** 2026-08-15
- **Scope:** Core architecture (`src/core/`), Android integration (`C:\Workspace\Project_Android\GbaEmulatorAndroid\`), and the correctness/performance posture measured by the credibility matrix. Documentation only — no code changes.
- **Method:** Direct reading of core sources; JNI/Kotlin bridge and presentation code; `docs/` roadmaps and device-soak evidence; mGBA public suite results in `build/test-results/`. OSS-core internals are characterized from public changelogs/docs and marked as such where not verified at source level.
- **Evidence anchors:** credibility matrix `build/test-results/credibility-matrix-20260814-210843-10140.md` (14 GREEN suites, `io-read` RED 51/130, `misc-edge` RED 6/12); the `video` target is **absent by baseline design** (verified separately via `tools/run-video-suite-all.ps1`, 7/7 GREEN) — not a regression. Device evidence `docs/controlled-beta-readiness.md:89` ("measured 1.4–2 fps with full stalls") and `docs/open-issues-status.md:105` ("1.4–2 fps → full stall (0 presents), coreUnderruns=0").

## 0. Executive Summary

The core is a correct-shape, heavily cycle-accounted **instruction-at-a-time interpreter** that passes 14 mGBA public CPU/timing suites, but its video path is architecturally out of step with mature cores: the whole frame executes first, and only then are all 160 scanlines rendered from **end-of-frame memory state with a single register snapshot** (`src/core/android_runtime.cpp:232-242`). Mature GBA cores couple video rendering/state sampling to emulated display timing rather than reconstructing every visible line from one end-of-frame state; implementations vary from scanline/HBlank-oriented approaches (mGBA — its changelog records HBlank-related latching/timing fixes) to finer per-pixel timing (SkyEmu's per-pixel PPU). Our end-of-frame render means no scanline sees the register/VRAM/palette/OAM state that was live when that line was scanned. This is a *correctness* gap — mid-frame video effects are rendered with the frame's final values. It is also a *performance* gap of its own: the scanline renderer scans all 128 OAM entries per pixel (~4.9M sprite evaluations per frame, `src/core/ppu_renderer.cpp:243`). Separately, the Android present path (Canvas drawBitmap on the main thread inside the Compose frame clock) is the source of the device's full presentation stall. The credibility matrix's RED targets (`io-read` 79/130 failures, all video registers; `misc-edge` H-blank flag timing) plus the `video` suite (intentionally excluded from the matrix baseline — verified separately via `run-video-suite-all.ps1`) must be re-baselined before the PPU workstream can be validated against an oracle.

## 2. The PPU Scanline-Render Gap in Detail

### 2.1 Why end-of-frame rendering is a correctness risk

`AndroidRuntime::step_frame_with_fetch_trace` runs the scheduler to `cycle_target = kCyclesPerFrame = 280,896` (`android_runtime.cpp:187-193`; `ppu_timing.hpp:34-35`), then renders all 160 scanlines with a single `PpuRenderControl` snapshot taken **after** the loop (`android_runtime.cpp:233-241`) and with the **end-of-frame** contents of VRAM, palette RAM, OAM, and memory. Real hardware scans each line at the line's own time, so every mid-frame change below is visible on the lines after it occurs — our renderer shows the frame-final value on **every** line:

- **Mid-frame BG scroll writes (HOFS/VOFS):** games (e.g. horizontal-scroll effects in Emerald's overworld transitions) update BG0-3HOFS between HBlanks to scroll per-line. Real hardware latches the scroll offset at the start of each scanline; we render every line with the final write. (The same register family appears in the `io-read` failures, but that suite exercises LCD MMIO read semantics — readability/open-bus/affine and split 32-bit access — which is independent of render timing; see §3.)
- **Palette swaps during HBlank:** sprite/palette cycling done in the HBlank IRQ (fading, water/aura effects) changes colors mid-frame; the scanline currently being drawn must use the palette state at its scan time, not the frame's final palette.
- **BG affine reference points (BG2X/BG2Y, PA-PD):** rotation/scale registers are updated per-line by the game to produce pseudo-3D; reads also have 32-bit split-latch semantics. Affine BGs are not rendered at all today (text-only fetcher, `ppu_background.cpp:59-111`; roadmap Phase 62 status: "True affine BG matrices … remain deferred", `docs/production-engine-roadmap.md:357-361`), and the io-read failures on `BG2PA…BG3Y_HI` show even the register read-back path is wrong.
- **OAM/VRAM updates between HBlank and VBlank:** games rewrite OAM and VRAM mid-frame (sprite flicker/reshuffle techniques); per-line rendering must read OAM/VRAM as of line scan time.
- **Window/BLD registers (`WIN0H`, `WININ`, `BLDALPHA`, `BLDY`):** window rects and brightness fade steps are frequently rewritten per HBlank; a single snapshot turns per-line windowing/fades into one static value for the whole frame. (mGBA's changelog records exactly these classes of fixes: "GB Video: Fix window being enabled mid-scanline", "GBA Video: Latch scanline at end of Hblank".)
- **Per-line OAM scan semantics:** real hardware selects the first 32 sprites per line and latches their attributes at line start; the renderer instead evaluates all 128 sprites per pixel (`ppu_renderer.cpp:243`), so it neither limits to 32 nor latches at line start — wrong in both directions.

The structural cause is one line of design: `PpuTiming::tick` (`ppu_timing.cpp:144-162`) advances line/cycle counters and raises IRQs/DMA, but nothing observes the HBlank boundary to latch or render. The renderer and the timing model are cleanly separated — which is exactly what makes the fix tractable (Section 2.3).

### 2.2 Is this the pacing root cause? No.

The measured device failure — "full stall (0 presents)" with `coreUnderruns=0` — is a main-thread presentation failure (present runs on `Dispatchers.Main` inside the Compose frame clock, `GameScreen.kt:265-267`), not an artifact of end-of-frame rendering; the frame budget is dominated by interpreter + renderer host cost and then blocked on the present path.

### 2.3 Workstream plan: scanline-interleaved rendering

**Goal:** each scanline is rendered from the memory/register state that was live when the PPU scanned that line, with rendering work decoupled from the execution loop.

**Design options.**

- **Option A — snapshot capture at HBlank, deferred render:** during the frame, at each `enter_hblank` event (`ppu_timing.cpp:239-246`), capture a per-line snapshot: the `PpuRenderControl` registers (or just the registers that can legally change mid-frame: DISPCNT, BGCTRL, HOFS/VOFS, affine params, WIN*, BLD*), plus scanline index and any OAM-visible state. Render 160 lines from the 160 snapshots after the frame, exactly as today's end-of-frame pass does. **Pro:** execution loop stays untouched (no renderer call mid-loop, no reentrancy into the memory bus from the scheduler); deterministic; smallest change to the core loop. **Con:** memory contents (VRAM/palette/OAM) are still read at render time, so mid-frame *memory* writes remain un-modeled — register latching (the dominant class, per Section 2.1) is fixed. Note: `io-read` is a separate LCD MMIO read-semantics problem, independent of render timing (see §3); no `io-read` outcome is predicted here.
- **Option B — inline render at each HBlank boundary:** call `renderer_.render_scanline(memory, control_at_hblank, line)` from inside `enter_hblank` (or from `advance_devices` after the event), using live memory. **Pro:** fully correct — VRAM/palette/OAM/registers all sampled at scan time; matches mGBA's model (per-scanline draw at HBlank, threaded proxy draws "in the gaps"). **Con:** renderer runs inside the scheduler's device-tick path (reentrancy into `MemoryBus` reads from a callback the bus may be mid-transaction on — needs care); render cost shifts into the per-frame critical path (currently it is already in the frame path, so net neutral); harder to bisect.
- **Recommendation:** Phase 1 with Option A (register snapshots) as the correctness baseline for the `video`/scanline-behavior suites, then Phase 2 with Option B, kept behind a flag, once the snapshot path proves deterministic. `io-read` is out of scope for this workstream (independent MMIO semantics, see §3).

**Determinism and regression strategy.** Re-baselining must precede the renderer redesign, in this explicit order: (1) fix `io-read` independently — it is an LCD MMIO read-semantics problem (`is_lcd_control_readable` / `lcd_control_read_mask` / `read_lcd_control`, `ppu_timing.cpp:47-117`: what is readable, open-bus behavior, affine register semantics, split 32-bit access), not a render-timing problem, and scanline latching will not repair it; (2) restore `misc-edge` HBlank-flag timing; (3) establish the missing `video` oracle target; (4) baseline the renderer (frame hashes on the synthetic corpus); (5) only then undertake the scanline-latching redesign, validated against the re-baselined suites. Then:

1. Re-run the mGBA `video` suite as the primary correctness gate (`tools/run-mgba-suite.ps1 -Suite video`; the `-VideoProbe basic-mode-3-actual` oracle harness already exists per `docs/PERFORMANCE.md:76-80`).
2. Build frame-hash baselines for the existing synthetic renderer corpus (the core is fully deterministic — `state_hash()` covers CPU/memory/scheduler/PPU/APU, `core_session.cpp:189-204`) so a renderer change either reproduces identical frame hashes or produces a reviewed diff.
3. Gate on the suite + a small video-oracle corpus (fixed-seed ROMs with known mid-frame effects) before merging; keep the old renderer behind a compile flag for the first landing.

**Performance implications.** Today's renderer cost is per-pixel OAM scanning (~4.9M sprite evaluations/frame at 240×160×128); interleaving does not change per-frame cost, it only moves it earlier in the frame. Two compounding levers: (a) pre-scan OAM once per line with the 32-sprite cap (Section 3, P0) — reduces sprite evaluation ~130×; (b) with Option B, rendering one line at a time lets a later phase cache palette/VRAM rows per line. Interleaving also enables the future "draw in the gaps" threading model (render HBlanks on a worker) that the current burst-of-160-lines model cannot use.

**Phase breakdown.**

- **P0 — Design doc (this audit is the seed):** choose A vs B, define the `PpuLineSnapshot` struct (registers only, then full state), define the flag and the regression gate. ~1 week.
- **P1 — Snapshot capture (Option A):** capture per-line register state at `enter_hblank` (`ppu_timing.cpp:239`), store `std::array<PpuRenderControl-ish, 160>`, render from snapshots in the post-frame pass. No `io-read` outcome is predicted here — that suite covers LCD MMIO read semantics independent of render timing (see §3); keep the gate green on all CPU suites and the newly baselined `video` target. ~1-2 weeks.
- **P2 — Inline render (Option B):** render at HBlank boundary with live memory, behind a flag; handle bus reentrancy (read-only `MemoryBus` accessor or deferred render queue). Re-verify against snapshots for determinism. ~2 weeks.
- **P3 — Oracle comparison:** video suite + video-oracle corpus + frame-hash diffing on real ROMs (Pokemon Emerald early-game), publish a before/after correctness delta; only then consider removing the end-of-frame path. ~1 week.

## 3. Prioritized Fix Sequence (P0 / P1 / P2)

**P0 — evidence and pacing (this week).** Items marked IN FLIGHT are being fixed in parallel on 2026-08-15.

1. **IN FLIGHT — Per-frame `state_hash` gating:** ROM-wide hash computed every frame in `step_frame` (`android_runtime.cpp:254`), surfaced through JNI (`gba_jni.cpp:213`) into the Kotlin logger (`PlaytestDataLogger.kt:16-28`); gate behind the existing `state_hash_enabled_` flag (`android_runtime.cpp:125-131`) and stop computing it per frame.
2. **IN FLIGHT — Per-frame video diagnostics gating:** `analyze_framebuffer` builds a 65,536-entry color histogram per call (`android_runtime.cpp:29-78`); currently DEBUG-gated in Kotlin (`GameScreen.kt:257-260`) but the native side runs unconditionally when called — remove from the frame path entirely.
3. **IN FLIGHT — Present off the main thread:** `withContext(Dispatchers.Main) { presentOnSurface }` inside the Compose frame clock (`GameScreen.kt:265-267`) blocks the UI thread and is the documented "full stall (0 presents)" (`open-issues-status.md:105`); move presentation to the emulation thread (SurfaceView is thread-safe for lockCanvas/unlockCanvasAndPost) or a dedicated present thread with triple-buffered RGB565 surfaces.
4. **IN FLIGHT — Logger gating:** `PlaytestDataLogger.logFrame` enqueues metrics (including `stateHash`) for every frame (`PlaytestDataLogger.kt:52-57`); gate behind a flag (e.g. `BuildConfig.DEBUG`) or sample N frames.
5. **Re-baseline the credibility matrix, in order:** (1) fix `io-read` as an independent LCD MMIO read-semantics problem (readability/open-bus/affine register semantics — `ppu_timing.cpp:47-117`), (2) restore `misc-edge` HBlank-flag timing, (3) add the missing `video` target with the existing oracle probe, then (4) baseline the renderer — required before any PPU refactor can be validated; scanline latching does not repair `io-read`.
6. **Renderer hot loop (perf, low risk):** enforce the hardware 32-sprite-per-line cap with a per-line OAM pre-scan in `PpuRenderer::render_scanline` (`ppu_renderer.cpp:243` scans all 128 per pixel); ~130× fewer sprite evaluations per frame with no behavioral change for conforming games.

**P1 — PPU correctness (this month).** The scanline-interleaved rendering workstream (Section 2.3, phases P1-P3): per-scanline register latching (HOFS/VOFS/affine/WIN/BLD), then inline render at HBlank. Includes MOSAIC-register dimensions, OBJ-window, alpha blend (`BLDALPHA` first/second target — currently brightness-only, `ppu_renderer.cpp:105-135`), and affine BG fetch (BG2/BG3 PA-PD/X/Y). These are renderer-correctness items; the `io-read` MMIO read-semantics fixes land independently in P0 and are not addressed by scanline latching.

**P2 — performance architecture (next).** Interpreter throughput (block predecode → candidate translation for hot loops, a strategy used by dynarec-based desktop cores such as VBA-M), renderer per-line caching, APU SOUNDBIAS-driven sample rate (`apu.cpp:109-113`), LTO release builds, GLES presentation (Section 4).

## 4. Future Android Integration Options

- **Presentation: GLES/EGL native surface vs Canvas.** Current path is CPU `Canvas.drawBitmap` with `FILTER_BITMAP_FLAG` bilinear scaling (`GameViewportSurface.kt:18-81`) — cheap to write, expensive at 1.4-2 fps. Public docs describe VBA-M's Android port as OpenGL ES-based. The minimum GLES step: keep the RGB565 `short[]` but upload via `glTexSubImage2D(GL_RGB, GL_UNSIGNED_SHORT_5_6_5)` into a scaled quad with a nearest-neighbor shader (bilinear for smoothing optionally). The bigger step: keep the framebuffer native-side (EGL/`ANativeWindow` pbuffer, or `GL_OES_EGL_image` from a native buffer) and eliminate the JNI `SetShortArrayRegion` copy (`gba_jni.cpp:257-272`) entirely — ~76 KB/frame today, negligible, but it removes the JNI barrier to a present thread.
- **Audio: AAudio vs Oboe.** The app already uses Oboe (`apu_audio_oboe.cpp:1-15`, `find_package(oboe REQUIRED CONFIG)` in `CMakeLists.txt:42,61`), which abstracts AAudio with an OpenSL ES fallback — keep Oboe; drop to raw AAudio only if a specific device's latency needs the direct API. `coreUnderruns=0` shows audio is not the pacing bottleneck.
- **LTO for release builds.** `CMakeLists.txt` sets `-O3` but no `-flto` (`CMakeLists.txt:55-59`); VBA-M's release builds are described as LTO'd. Add `-flto` (and `-ffat-lto-objects` for debug symbol sanity) to the release variant of `gbaemulator`, plus AGP R8/ProGuard shrink flags on the Kotlin side. Expect single-digit percent core speedup — meaningful at the current 1.4-2 fps.
- **Texture upload path.** If staying with a Java-visible framebuffer, pre-allocate the `ShortArray` once (already done — `recycledPixels`, `GameScreen.kt:219`) and keep `copyPixelsFromBuffer` in a `Bitmap.Config.RGB_565` (no format conversion); if moving to GLES, upload from the same buffer directly to the texture unit on the present thread and drop the Bitmap entirely.

1. Land the four IN FLIGHT integration fixes (per-frame `state_hash` gating, per-frame video diagnostics gating, present-off-main-thread, per-frame logger gating) and re-run the device soak to re-measure pacing.
2. Re-baseline the credibility matrix in order — fix `io-read` as an independent LCD MMIO read-semantics problem (BG0HOFS family), restore `misc-edge` HBlank-flag timing, add a `video` oracle target, then baseline the renderer — before any PPU refactor; scanline latching does not repair `io-read`.
3. Cap sprite evaluation at the hardware 32-sprites-per-line limit with a per-line OAM pre-scan in `PpuRenderer` (largest single renderer perf lever, low risk).
4. Begin the scanline-interleaved rendering workstream with a P0 design doc choosing snapshot-deferred (A) vs inline (B) rendering at HBlank boundaries, with per-scanline register latching scoped.
5. Convert the end-of-frame render into per-scanline rendering and gate it behind frame-hash diffing plus the mGBA video suite and video-oracle baselines to prove no regression.
